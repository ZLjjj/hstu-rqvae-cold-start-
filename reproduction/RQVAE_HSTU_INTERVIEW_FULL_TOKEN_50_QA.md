# Full-Token Route B：新增 50 个面试问题与参考答案

## 十一、Full-Token 架构与 Token 设计（101—110）

### 101. 为什么还要做 Full-Token Route B 实验？

参考答案：旧 Route B 的历史仍是一物品一向量，只在输出端生成目标物品的三级码，因此不能验证完整 Semantic ID 序列建模。Full-Token 实验把历史和目标统一到 Token 空间，让 HSTU 同时学习物品内部的 `c1→c2→c3` 与物品之间的 `上一物品 c3→下一物品 c1`。它要回答的是：旧 Route B 较差究竟来自简化结构，还是来自 Semantic ID 生成目标本身。

### 102. Full-Token Route B 与旧 Route B 的核心区别是什么？

参考答案：旧 Route B 先把一个物品的三码拼成单个 50 维向量，历史长度仍按物品计；生成后两级时只把前缀码向量加到固定用户上下文。Full-Token 则把每个历史物品展开成三个 Token，HSTU 在完整 Token 序列上因果建模，生成 `c1` 和 `c2` 后也会把它们真正追加回序列并重新编码。前者是“物品级编码器+层级输出头”，后者才是 Token 级自回归模型。

### 103. Full-Token 的词表如何编号？

参考答案：设每层码本大小 `K=1024`，定义 `PAD=0`、`BOS=1`，普通码使用 `token(level,code)=2+level×K+code`。因此 level-0 范围是 2—1025，level-1 是 1026—2049，level-2 是 2050—3073，总词表大小为 `2+3×1024=3074`。这种编号可以从 Token 唯一反解出层级和原始码值。

### 104. 为什么不同层的相同 code 必须映射成不同 Token？

参考答案：RQ-VAE 的三个码本参数独立，level-0 的 code 12 和 level-2 的 code 12 只是编号相同，语义并不相同。若共享 Token ID，模型会把粗粒度码和细粒度残差码混为一谈。层级偏移让三层拥有互不冲突的身份，同时还能使用统一的输入 embedding 表。

### 105. 历史物品序列具体如何展开？

参考答案：历史 `[i1,i2]`，若 `i1→(c11,c12,c13)`、`i2→(c21,c22,c23)`，则展开为 `[BOS,c11,c12,c13,c21,c22,c23]`。每个物品固定三个 Token，所以不需要额外 SEP 或 EOS；level-0 表示物品开始，level-2 表示物品结束。展开后一个物品不再只占一个 HSTU 位置。

### 106. Token embedding 如何利用 RQ-VAE 码本？

参考答案：模型建立 `[3074,64]` 的统一 embedding 表，把三层 `[3,1024,64]` 码本向量按层复制到对应 Token 行；PAD 行固定为零，BOS 随机初始化。64 维 Token 向量再投影到 HSTU 的 50 维空间。主实验设置 `freeze_semantic_token_embeddings=false`，所以历史输入和生成反馈共用一张由 RQ-VAE 初始化、可被推荐损失微调的表。

### 107. 已经做了层级偏移，为什么还要 level/type embedding？

参考答案：层级偏移解决的是 Token 身份冲突，level embedding 则显式告诉 HSTU 当前位置承担 PAD、BOS、L0、L1 或 L2 中哪种结构角色。最终输入由码本初始化的 Token 向量、展开后的绝对位置向量和层级类型向量相加，使模型更容易学习固定的三级语法。

### 108. Full-Token 如何处理时间戳？

参考答案：同一个物品的三个 Semantic Token 复制同一个原始交互时间戳，例如电影时间为 160，则 `c1/c2/c3` 都使用 160；BOS 使用首个有效历史物品的时间。这样物品内部时间差为零，物品之间仍保留真实时间跨度，可以继续使用 HSTU 的相对时间偏置。

### 109. 历史物品缺少 Semantic ID 时怎么办？

参考答案：主实验使用显式 `filter` 策略：缺少完整三码的历史物品被过滤并计数，不会静默变成 PAD，也不会利用测试目标内容回填。这样可以避免把“内容缺失”和“序列补齐”混为一类，但代价是用户历史可能缩短，且缺码物品的行为信号被丢失。

### 110. 为什么最大 Token 长度是 604，而不是 601？

参考答案：纯历史最多为 `1+3×200=601`，其中 1 是 BOS。训练时还需要接入一个目标物品的三个真实 Token 做严格右移，因此上限是 `1+3×(200+1)=604`。推理生成 `c1/c2` 时最长分别约为 602 和 603。历史长度扩大约三倍后，自注意力矩阵面积理论上扩大约九倍。

## 十二、Full-Token 训练与因果建模（111—120）

### 111. Full-Token 的 next-token 训练目标是什么？

参考答案：对完整序列 `[BOS,c11,c12,c13,c21,c22,c23]` 严格右移，输入为除最后一个 Token 外的部分，目标为除 BOS 外的部分。模型学习 `c1→c2`、`c2→c3`，也学习 `上一物品 c3→下一物品 c1`。这与旧 Route B 只在最终用户上下文上计算三次分类损失不同。

### 112. 哪些位置参与训练损失？

参考答案：所有有效且非 PAD 的右移目标都可参与监督，并根据目标所属层级进入对应分类头。主配置默认不计算 `BOS→首个历史物品 c1`，因为此时没有用户历史，只会强化全局流行度；其余 L0、L1、L2 位置均参与。缺码过滤产生的空位也不会进入损失。

### 113. 为什么关闭 BOS 到第一部物品的损失？

参考答案：从 BOS 预测用户第一部电影没有个性化上下文，最容易学到的是全局热门分布，而不是序列偏好。严格的下一物品推荐更关心已有至少一次行为后的转移，因此主实验关闭这一项。它被做成配置开关，方便后续验证流行度先验是否有帮助。

### 114. 为什么输出端使用三个 1024 分类头，而不是一个 3074 分类头？

参考答案：每个位置的目标层级是确定的，L0 位置不可能预测 L1、L2、PAD 或 BOS。三个独立的 1024 分类头只比较当前层的码，减少无意义负类和计算量，也便于分别观察粗码、残差码的难度。输入端仍使用统一的 3074 Token ID，以支持完整序列编码。

### 115. 分层 loss 和 accuracy 有什么诊断价值？

参考答案：模型分别记录 L0、L1、L2 的交叉熵、准确率和样本数，可以判断问题发生在粗粒度兴趣预测还是细粒度路径补全。如果 L0 较好而 L2 很差，说明粗语义可预测但完整物品路径过细；如果三层都偏向暖码，则可能是冷路径缺乏正监督，而不只是 Beam 搜索问题。

### 116. 如何验证因果 Mask 没有泄漏未来 Token？

参考答案：除了检查上三角未来位置被屏蔽，还应做干预测试：只修改某个未来 Token，比较它之前各位置的 HSTU 输出，结果必须保持一致。项目单测同时检查严格右移、PAD loss mask 和未来 Token 不影响早期输出，避免模型训练时偷看真实目标。

### 117. Full-Token 是否彻底消除了 teacher forcing 问题？

参考答案：没有。训练时预测后续 Token 使用真实前缀，推理时使用模型生成的 `c1/c2`，因此 exposure bias 仍然存在。改进之处是生成 Token 会真正反馈进 HSTU，训练和推理都遵循同一种 Token 序列形式；但错误前缀导致后续分布漂移的问题仍需 scheduled sampling、sequence-level loss 等方法处理。

### 118. “把生成 Token 真正反馈给 HSTU”是什么意思？

参考答案：预测 `c1` 后，将其转换为带层级偏移的 Token，追加到历史序列，再运行 `HSTU(history+c1)` 预测 `c2`；随后追加 `c2`，用 `HSTU(history+c1+c2)` 预测 `c3`。旧 Route B 只在固定上下文上加前缀向量，没有让注意力重新处理生成历史，因此两者并不等价。

### 119. 为什么训练使用小 micro-batch 加梯度累积？

参考答案：Token 化使序列长度约扩大三倍，注意力矩阵约扩大九倍，直接保持原 micro-batch 容易显存不足。基础配置使用 micro-batch 32、累积 4 次梯度，等效 batch size 约为 128。服务器摘要中的 batch size 128应理解为有效 batch；BF16 进一步降低显存并提高吞吐。

### 120. 为什么主实验允许 Token embedding 微调？

参考答案：RQ-VAE 码本是按内容重建目标学习的，不一定最适合下一行为预测。允许微调可让码本初始化适应推荐损失，也使历史输入与生成反馈使用统一、可学习的语义空间。代价是原始内容几何可能漂移，因此冻结与可训练码本应作为后续消融，不能仅凭本次主实验判断哪种更好。

## 十三、Trie、Beam、Exact 与工程实现（121—130）

### 121. 新版 Trie 约束相比旧 Route B 改了什么？

参考答案：旧实现先从全部 1024 个码中取一小批高分码，再过滤不合法前缀，可能把排名稍低但合法的子码提前丢掉。新版先根据 Trie 取得当前前缀的全部合法子码，再只在合法集合中归一化和排序。这样前缀约束不再额外造成候选收缩。

### 122. 自适应 Beam 是如何工作的？

参考答案：主配置从 beam 32 开始，如果映射后的唯一物品不足目标数量，就将宽度逐步翻倍，最大到 256，目标是得到 200 个唯一物品。它比固定 beam=8 更符合 Top-200 任务，但也显著增加逐级前向、排序和路径管理成本。

### 123. 新实验的 Beam 覆盖结果怎么样？

参考答案：最终实际 Beam size 达到 256，Beam 映射前平均得到约 217.616 个唯一物品，远高于旧 Route B 的约 6.263 个；平均 Exact 补齐降到约 4.263 个。说明合法子码优先和大 Beam 基本解决了“生成候选数量不足”的工程问题。

### 124. 平均已有 217.6 个唯一物品，为什么仍然需要 Exact 补齐？

参考答案：217.6 是跨用户平均值，不代表每个用户都达到 200；部分用户在过滤历史、处理冲突或路径映射后仍不足 200，因此平均还需补约 4.263 个。均值还可能掩盖长尾用户，应该进一步报告分位数和触发补齐的用户比例。

### 125. Full-Token 如何处理完整语义码冲突？

参考答案：完整路径映射到所有对应物品，冲突物品共享完全相同的路径概率，不额外加入 Item ID residual。本地 bridge 中 3416 个有效物品形成 3376 条唯一路径，有 36 条冲突路径、影响 76 个物品。这是纯 Token 生成在 item-level 排序上的不可辨识上限。

### 126. Full-Token Exact Scorer 如何计算物品分数？

参考答案：对候选路径 `(c1,c2,c3)` 严格计算 `log p(c1|history)+log p(c2|history,c1)+log p(c3|history,c1,c2)`。每一级条件都来自把真实前缀 Token 追加到历史后的 HSTU 输出，而不是旧 Route B 的固定上下文加法近似。单测用逐级三次前向验证批量分数完全一致。

### 127. Exact Scorer 为什么按前缀共享计算？

参考答案：许多物品共享 `c1` 或 `(c1,c2)`，如果逐物品重跑 HSTU 会大量重复。实现按空前缀、相同 `c1`、相同 `(c1,c2)` 分组，并按 `exact_prefix_batch_size=256` 批量计算。这样不改变精确路径概率，但减少重复前缀前向和峰值显存。

### 128. Beam-only、Beam+Exact 和 Exact-global 三种口径有什么区别？

参考答案：Beam-only 只评价生成搜索得到的候选；Beam+Exact 是实际主 Top-200，在 Beam 不足时用全路径评分补齐；Exact-global 则完全按所有有效物品的精确路径概率排序。三者分别诊断搜索覆盖、实际返回结果和模型概率本身，不能混成一个指标解释。

### 129. 为什么 Beam-only cold AUC=0.001623 不能与 cold AUC=0.077678 直接比较？

参考答案：项目中的 Beam-only AUC 基于截断的 Top-200 排名，未命中被视为列表末端，实质上更像归一化的头部排名分数；0.077678 则来自 Exact Scorer 的全有效候选排名。二者候选范围不同，不是同一个全局 AUC 定义。判断概率模型应以 Exact-global cold AUC 为准，Beam-only 更适合配合 HR 和候选覆盖分析。

### 130. Full-Token 实验的资源开销是多少？

参考答案：加速版在 RTX 4090 D、PyTorch 2.5.1、BF16 和 FBGEMM GPU 环境中运行约 5 小时 29 分，最佳 checkpoint 为 epoch 49。GPU 平均利用率约 57.01%、最高 98%，采样峰值显存约 4698MB，模型记录的测试峰值约 3033.72MB，平均功耗约 165.72W。由于硬件与验证协议不同，这些数据不能直接证明它比旧 Route B 快或慢多少。

## 十四、Full-Token 结果与原因分析（131—140）

### 131. Full-Token Route B 的最终结果如何？

参考答案：全量测试 Overall AUC=0.788509、HR@100=0.378808、NDCG@100=0.113028、corrected MRR=0.054830；Cold AUC=0.077678、Cold HR@100=0.001835、Cold NDCG@100=0.000395、Cold corrected MRR=0.000076；Warm AUC=0.859010、Warm HR@100=0.416197、Warm NDCG@100=0.124199。结果显示整体改善主要来自暖物品。

### 132. Full-Token 相比旧 Route B 改善了哪些指标？

参考答案：Overall HR@100 从 0.263576 升到 0.378808，相对提高 43.72%；Overall NDCG@100 从 0.080531 升到 0.113028，提高 40.35%；corrected MRR 从 0.041626 升到 0.054830，提高 31.72%。因此完整历史 Token 化和更充分搜索确实提高了总体序列推荐质量，但这不等价于提高冷启动。

### 133. 为什么 Full-Token 对暖物品提升明显？

参考答案：暖物品的语义 Token 和转移模式在训练中反复出现，完整序列建模可以利用码级共现、物品内部路径结构和跨物品转移；更大的自适应 Beam 也提高了候选覆盖。因此 Warm AUC 达到 0.859010、Warm HR@100 达到 0.416197。模型主要学强了训练分布中的暖路径。

### 134. 为什么完整 Token 化仍没有改善冷启动？

参考答案：冷物品不作为训练正目标，它们的完整三级路径，尤其是细粒度后缀，缺少用户行为监督。Full-Token 虽然改进了序列形式和搜索覆盖，但训练目标仍是最大化暖物品 Token 的似然，容易进一步强化暖路径。Trie 知道冷路径“存在”，并不意味着模型知道哪个用户会喜欢该冷物品。

### 135. 如何解读 Full-Token cold AUC=0.077678？

参考答案：Exact-global cold AUC 表示冷目标平均只击败约 7.77% 的有效候选，甚至低于普通 HSTU baseline 的 0.088247 和旧 Route B 的 0.228927。这说明问题不是正确路径没进入 Beam，而是完整 Token 概率把冷路径系统性排在全局尾部，呈现明显的暖物品或高频 Token 偏置。

### 136. Full-Token 的 cold HR@K 说明了什么？

参考答案：Cold HR@10=0，Cold HR@50/100/200 都为 0.001835。结合约 545 条冷测试样本，意味着只有约 1 条冷目标进入 Top-200，并且它位于第 11—50 名；第 51—200 名没有新增冷命中。扩大 Beam 解决了候选数量，却几乎没有增加正确冷目标。

### 137. Exact-global 与 Beam+Exact 的 cold HR@100 相同意味着什么？

参考答案：两者 Cold HR@100 都为 0.001835，且 Cold NDCG@100 也都约 0.0004，说明即使完全按照 Exact 路径概率排序，冷目标仍进不了 Top-100。搜索近似已不是主要矛盾，概率模型对冷路径的打分本身才是核心瓶颈。

### 138. 新实验完成后，为什么 Route A 仍是最佳冷启动路线？

参考答案：Route A 的 cold AUC=0.592034、cold HR@100=0.102752、cold NDCG@100=0.021144，远高于 Full-Token 的 0.077678、0.001835 和 0.000395。Route A 直接在连续语义向量空间做匹配，可以利用相似方向泛化；生成路线要求三级离散路径都获得高概率，对未见冷路径更苛刻。

### 139. Full-Token Overall AUC=0.788509 应如何评价？

参考答案：它高于旧 Route B 的 0.748485，但仍低于 HSTU baseline 的 0.824046、Dense 的 0.847237 和 Route A 的 0.857546。结合 HR@100=0.378808 可知新模型不是总体最优，只是缩小了旧生成路线与向量检索路线的差距。不能只强调相对提升而忽略绝对排名。

### 140. 最佳 checkpoint 选择协议有什么局限？

参考答案：加速版训练 50 轮，每轮只使用固定 5 个验证 batch 选择 checkpoint，最佳为 epoch 49，之后再做全量测试。这降低了验证成本，但局部验证指标可能噪声较大，也与旧实验的完整验证协议不完全一致；原项目验证/测试目标重复的问题也没有因此消失。结果适合作为工程验证，但仍需完整独立验证集和多随机种子确认。

## 十五、研究判断、改进与简历表达（141—150）

### 141. Full-Token 实验是否验证了最初假设？

参考答案：只验证了一半。它证明旧 Route B 的简化结构确实限制了整体推荐能力，因为完整 Token 化后 Overall HR、NDCG 和 MRR 明显上升；但“完整 Token 化会改善冷启动”的假设被否定，Cold AUC 反而显著下降。这个结果把问题从“搜索覆盖不足”进一步定位到“冷路径概率学习失败”。

### 142. Full-Token 冷启动失败的最根本原因是什么？

参考答案：严格冷物品没有作为 HSTU 正目标出现，而生成模型直接学习 Token 出现概率，训练信号天然集中在暖路径。内容侧码本可以告诉模型冷物品与哪些物品语义相似，却不会自动产生用户对冷物品完整路径的偏好概率。尤其后两级接近物品级细分标签，共享监督不足时会把冷路径压到尾部。

### 143. 为什么“共享 Semantic ID”没有自动带来生成泛化？

参考答案：共享通常集中在粗粒度前缀，而物品最终得分是三级条件概率之和。冷物品即使共享高概率 `c1`，其独特或低频的 `c2/c3` 仍可能获得很低概率；硬分类还把语义相近但不同编号的码视为完全不同类别。因此码本共享不等于完整路径概率共享，连续向量匹配往往更容易做近邻泛化。

### 144. Full-Token 的训练目标是否过度关注物品内部补码？

参考答案：每个物品包含三类转移：跨物品的 `上一c3→下一c1`，以及物品内部的 `c1→c2`、`c2→c3`。实现对三个层级 loss 取平均，因此约三分之二的结构角色与补全当前物品后缀有关，只有 L0 直接承担下一物品粗码预测。后续可提高 L0 或跨物品转移权重，但必须作为独立消融验证。

### 145. 下一步怎样针对冷路径概率进行改进？

参考答案：优先考虑内容感知的输出头和语义平滑损失，让相近码获得相近概率；用全部物品内容做无交互预训练，使冷路径的 Token 和前缀至少被建模；再将生成模型作为粗召回，与 Route A 连续语义得分或轻量精排融合。所有方法都必须保证不使用冷物品交互标签，并单独报告纯生成与融合结果。

### 146. 能否把整体提升完全归因于 Full-Token 结构？

参考答案：不能。新实验同时把固定 beam=8 改成自适应 beam 最高 256，训练采用 50 轮和固定 5 个验证 batch，并运行在不同的 BF16、FBGEMM 和 GPU 环境中。HR 和 NDCG 提升可能同时来自序列结构与搜索覆盖；Exact-global 概率指标更能隔离搜索影响，但仍受训练协议影响。需要匹配 Beam、训练预算和验证协议的消融才能做因果归因。

### 147. 新旧 Route B 的运行时间可以直接比较吗？

参考答案：不可以。旧 Route B 约 4 小时 15 分，新 Full-Token 约 5 小时 29 分，但二者硬件、FBGEMM 可用性、验证频率、Beam 宽度、序列长度和 Exact 实现均不同。可以说 Full-Token 绝对成本仍高，并报告本次资源数据；不能简单声称它只慢 29% 或某个精确比例。

### 148. 一个冷指标变差的实验有什么价值？

参考答案：它排除了“只要把历史完整 Token 化并扩大 Beam 就能解决冷启动”的简单解释，并通过 Beam 覆盖、Exact 全局排序和资源监控定位真正瓶颈。这类负结果展示了实验设计、实现审计和归因能力，比只展示一个经过挑选的正指标更能体现研究与工程成熟度。

### 149. Full-Token 实验应该怎样写进简历？

参考答案：可以写成：“实现三级 Semantic ID 全历史 Token 化、分层 next-token 训练、合法 Trie 自适应 Beam 与前缀共享 Exact Scorer；将旧生成路线 Overall HR@100 从 0.2636 提升至 0.3788，并通过 Exact-global 评估发现 cold AUC 降至 0.0777，定位瓶颈为冷路径概率学习而非候选覆盖。”不要写成“Full-Token 解决了冷启动”。

### 150. 加入 Full-Token 后，项目的最终结论是什么？

参考答案：五组实验表明：普通 HSTU 最擅长暖物品精细记忆；Dense 提供有限内容泛化；Route A 在当前协议下冷启动最好；旧 Route B 同时受概率建模和搜索覆盖限制；Full-Token 与大 Beam 改善了整体生成质量和候选数量，却进一步强化暖路径，未改善严格冷启动。最可靠的方向仍是 Route A 及 ID+Semantic 融合，生成路线则需要重做冷路径监督与连续语义泛化机制。
